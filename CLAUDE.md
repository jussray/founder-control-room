## Truth Lease and future-you / future-me safety

A fact may be correct when checked and unsafe when reused later. A hash proves identity, not continued reality.

At consequential merge, deploy, schedule, publish, completion-claim, provider, and launch boundaries:

1. identify the load-bearing claim and dependencies;
2. re-observe the authoritative current source;
3. classify current / stale / invalidated / unknown;
4. use present-tense language only while the required evidence is current;
5. preserve older evidence as historical provenance;
6. never let Current You preference override contradictory objective provider/runtime evidence;
7. never let FutureYou advice become evidence or approval.

Use the generic Truth Lease only where no equivalent or stronger domain-specific temporal gate already exists. Founder-content direct publication already has a stronger temporal revalidation path and should not be weakened for uniformity.

## Founder-owned progress publishing / Sauce Guard

The product goal is that Juss can publish verified progress about Juss's own products **from Founder Control Room** while keeping the implementation recipe private.

Public-safe story may include what changed, why it matters, what was learned, an approved public proof, and an honest unresolved next gate.

## Never signal success on failure

Do not show a success message or set a success flag inside a `catch` block.

If an operation throws or returns an error, the UI must reflect failure. Success may only be shown after the operation has completed successfully and its result has been verified.

This rule prevents false-positive UX where a user believes an action completed even though the underlying operation failed. A known example was a reminder interface reporting that a reminder was set after scheduling had thrown.

## Branch hygiene

Maintain one active implementation branch and one pull request per logical change.

- Branch once from current `main`.
- Use descriptive names such as `fix/*`, `chore/*`, or `feat/*`.
- Continue corrections, review changes, and conflict resolution on the canonical branch when its base remains authoritative.
- When `main` moves and exact-head authority is invalidated, preserve the old PR as historical and reacquire the focused change on current main rather than inheriting stale green.
- Do not create duplicate active merge candidates for convenience.

See [`REPO_HEALTH_DUPLICATES.md`](REPO_HEALTH_DUPLICATES.md) for the full duplicate-work and branch policy.

## Implementation Discipline

Continue the same reasoning style while implementing code. Do not perform analysis once, then abandon it when editing begins.

After meaningful changes, re-observe repository state, tests, schemas, provider behavior, runtime evidence, truth age, and documentation state.

The Hormozi pass must ask whether the desired outcome and proof are strong enough to justify time delay, effort, complexity, and ongoing maintenance. It may not invent demand or traction.

The Bill Gates pass must identify the bottleneck, highest-leverage correction, reusable standard, and what should not be automated or scaled yet.

The Elon Musk pass must question the requirement, delete unnecessary complexity before optimizing it, simplify the remaining path, shorten the feedback loop without weakening proof, and automate only after repeatable success. It may not delete approval, privacy, audit, rollback, evidence, truth, or sauce boundaries.

Compilation proves compilation. Unit tests prove tested behavior. CI proves repository workflow execution. Runtime observation proves deployed behavior. Documentation consistency proves only documentation consistency. Never collapse those into one cheerful but fictional green checkmark.

## Documentation truth

Truth-sensitive implementation/provider/authority changes must refresh `README.md` and the applicable current-state docs in the same bounded change.

Run `Documentation Truth` on the exact PR head and again on merged main. Historical material may remain, but stale present-tense guidance must be labeled historical/superseded or redirected to current authority.

Do not freeze a hard-coded “current main SHA” into durable prose. Exact SHAs belong in evidence/provenance; current identity is resolved at use time.

After every merge, re-read current main, relevant provider/runtime evidence, documentation truth, and the next launch bottleneck before continuing.

## Required Loop

1. Observe exact branch, data source configurations, current documentation, and display boundaries.
2. Complete 5W1H and identify authority, temporal, privacy, or safety gaps.
3. Run Redteam I on the premise and Redteam II on the selected solution.
4. Use Lindy/L99/OODA plus Product Design and Data Analytics to choose the smallest reversible path.
5. Apply Hormozi/Gates/Musk pressure to remove low-value complexity without deleting safety.
6. Run the narrowest valid type, lint, unit, build, contract, Documentation Truth, and Playwright checks for the touched path.
7. Re-read exact main/head before merge; stale green is historical only.
8. Report proven, inferred, stale, superseded, blocked, unknown, and next owner separately.
9. Post-merge, re-observe documentation and provider/runtime truth.
