# Control Room FutureYou Leverage

## Trigger

Use when choosing the next task, repair, automation, integration, standard, or investment across Founder Control Room and the wider portfolio.

## Purpose

Select the highest-leverage verified next action for Future Juss without inventing revenue, probability, urgency, or authority.

## Operating sequence

```text
ULTRATHINK
→ REDTEAM I: should this work exist?
→ LINDYMODE: will it remain useful?
→ /futureyou: what compounds?
→ REDTEAM II: how could the selected move fail?
→ OODA: act minimally and verify
```

## Candidate requirements

A candidate action must identify:

- verified current state;
- founder or user outcome;
- authoritative repository and owner;
- dependency and blocker;
- authority required;
- evidence needed;
- rollback;
- what future work becomes easier if it succeeds.

Reject or quarantine candidates built mainly from assumption, vanity metrics, stale plans, duplicated systems, or missing authority.

## Leverage dimensions

Score comparatively, never as invented financial precision:

1. **Bottleneck relief** — removes a verified constraint.
2. **Reuse** — benefits multiple tasks, agents, repositories, or projects.
3. **Evidence gain** — turns uncertainty into durable truth.
4. **Authority preservation** — strengthens founder control, auditability, and rollback.
5. **User value** — improves a real user or operator outcome.
6. **Durability** — survives provider, model, or tool replacement.
7. **Risk reduction** — reduces privacy, security, operational, or release risk.
8. **Time-to-proof** — reaches a truthful result through a short feedback loop.

## Decision classes

Every recommendation must declare one authority class:

- `read` — inspect and report;
- `prepare` — create a branch, draft, plan, test, or reversible artifact;
- `decide` — requires founder choice before execution;
- `verify` — test or read back an already authorized action.

Do not present `prepare` as `execute`, or `read` as approval.

## Lindy screen

Prefer:

- repository-native contracts and tests;
- provider-independent interfaces;
- reusable skills and validators;
- fewer adapters and state transitions;
- explicit evidence and rollback;
- standards that reduce future decision cost.

Penalize:

- one-off dashboards without action value;
- premature automation;
- duplicated memory systems;
- provider lock-in without necessity;
- work that scales an unverified process;
- features whose primary evidence is enthusiasm.

## Red-team gates

Ask:

- What evidence would reverse this ranking?
- Are we optimizing the visible problem instead of the real bottleneck?
- Does this recommendation hide legal, privacy, billing, credential, or production authority?
- Could a smaller action create the same evidence?
- Are we confusing strategic importance with current readiness?
- Does the action improve Future Juss's control or create another system to supervise?

## Definition of done

The recommendation is grounded in current evidence, declares its authority class, identifies what it compounds, survives both red-team passes, has a short proof loop, and does not portray uncertain economics as fact.
