How approvals work

Every decision moves through the same states — never sideways, never skipped.

A queued request is not an approved one. A received request is not an executed one. The console keeps those apart on purpose.

1SUBMITTEDDecision package received. Nothing has run.
2VALIDATEDIdentity, expiry, exact head, and content hash checked.
3APPROVEDYou approved this exact commit and payload.
4EXECUTION_STARTEDSHA and checks revalidated. Any new commit voids it.
5EXECUTEDDone only when a receipt ID, exact SHA, and downstream witness are attached.
Security boundaries

Built for the request that shouldn't go through.

One-time decision IDs

An approval used once cannot be replayed against a later commit.

Exact payload hashes

What you approved is what runs — hashed, not assumed.

Short expiry windows

An unanswered request goes stale on its own. Nothing waits forever for a click.

Re-auth on risky actions

Spend, deploy, and credential changes ask again, every time.

Proof, not promises

Every execution returns an immutable receipt.

Not a screenshot. Not a claim. A record tied to the exact commit, founder decision, and downstream outcome.
