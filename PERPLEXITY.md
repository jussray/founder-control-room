## 5W1H — Required Before Every Research or Action Task

- **Who** — requester, decision owner, affected data subjects, execution authority.
- **What** — research question/outcome, non-goals, existing work/history to preserve.
- **Where** — exact repository, branch, data source, runtime, and provider boundary.
- **When** — lifecycle state, timing constraint, source freshness, Truth Lease/use boundary, rollback window.
- **Why** — verified founder decision or operational need.
- **How** — narrowest safe repository inspection, research scope, action, proof, and rollback.

## Truth Lease / stale-evidence rule

A source can have been correct when retrieved and still be unsafe at use time.

For unstable provider/API/runtime/metric/legal/standards or other time-sensitive facts:

1. record the exact source and observation time;
2. identify which conclusion depends on it;
3. re-search/re-read the authoritative source when the conclusion is about to become consequential;
4. classify old observations historical, stale, superseded/invalidated, or unknown when current proof is missing;
5. never let an older highly ranked source silently outrank a newer authoritative source;
6. never treat FutureYou/model synthesis as evidence; and
7. never let analytics renew truth or grant authority.

Use the repository Truth Lease where applicable, while preserving stricter domain-specific gates such as exact-head repository verification and founder-content temporal revalidation.

## Product Design + Data Analytics

Research for a product surface should help distinguish capability, configuration, authority, temporal truth, provider state, outcome, blocked state, and next action. A single green badge is insufficient when the underlying truths differ.

Analytics is observation-only. Prefer safe counts, rates, comparable windows, state transitions, proof coverage, latency, and stale/invalidation rates. Do not export private prompts, raw diffs, credentials, customer/private data, private metrics, internal provider payloads, or implementation sauce merely to enrich an analysis.

A partial day, rolling-window change, or non-comparable metric is not a verified decline. Use like-for-like comparisons and label incomplete windows.

Founder Control Room should be able to tell verified progress about Juss's own products from Juss's own product while protecting the private recipe.

Perplexity may help fact-check public claims or research context, but public research does not become private repository/runtime truth or publication authority.

Canonical separation:


Never put private repository evidence, credentials, raw implementation detail, unreleased roadmap, private metrics, customer/security data, internal evidence references, or proprietary mechanics into external search queries merely to improve a social post.

LinkedIn may use the stronger first-party FCR route. Other supported destinations may use bounded n8n/direct adapters only when actually configured and proven. Draft generation is not provider capability.

Investor email remains separately gated by the applicable standing policy plus recipient-specific qualification.

## FCR merge-review truth

The current FCR in-app merge membrane and the live GitHub repository ruleset are separate authority surfaces.

Research may inspect source contracts, but source code alone does not prove GitHub required approvals, stale-review dismissal, last-push approval, strict status freshness, review-thread requirements, or bypass actor/mode configuration. Those need fresh GitHub provider readback.

A model, bot, or author comment must never be represented as a qualifying non-author semantic review when the repository contract requires genuine independent review.

## Non-negotiable boundaries

- Do not expose credentials, private business/vendor/customer data, family-sensitive content, teen-sensitive content, legal-sensitive details, private prompts, private metrics, raw diffs, or proprietary mechanics in external search queries or outputs.
- Do not blend project-specific private data across research.
- Repository/provider/runtime evidence outranks web summaries when establishing current private project truth.
- Use primary external sources for unstable provider, standards, security, API, legal, or technical facts whenever possible.
- Research findings are evidence, not authorization to merge, deploy, add provider scope, rotate credentials, change auth/RLS, publish, send, spend, or perform destructive actions.
- MCP tool availability is capability, not permission.
- GitHub/repository MCP reads must not leak private configuration to external search services.
- Never invent dashboard state, provider configuration, deployment success, review/approval history, demand, revenue, citations, publication, or customer outcomes.
- For changed user-facing UI/runtime paths, Playwright evidence is required before calling the path done.
- Historical truth stays historical; do not rewrite old evidence merely because current truth changed.
- Never delete founder material/history merely to simplify a current narrative.

## Required research and action loop

1. Resolve exact current repository/provider identity before assuming an old target is still current.
2. Separate verified facts, inference, unknowns, stale/superseded evidence, and Current You intent.
3. Search primary sources narrowly for material external unknowns.
4. Run Redteam on premise and chosen solution separately.
5. Use Product Design + Data Analytics + Lindy + L99 + OODA to choose the smallest durable path.
6. Apply Hormozi to increase useful proof/value while reducing delay and burden.
7. Apply Gates to the bottleneck/leverage question.
8. Apply Musk to question/delete/simplify/feedback/automate-last without removing safety.
9. Hand off implementation-ready evidence tied to exact sources/timestamps.
10. After merge/provider change, re-observe current main, current provider truth, Documentation Truth, and the next gate.

Use narrow search first. Prefer exact error strings, route names, provider methods, release notes, specifications, and official documentation. Stop when more sources would not change the decision.

## Documentation Truth

When research reveals a README, current-state document, provider guide, PR description, issue, or AI operating contract is materially stale, classify the old statement instead of silently using it.

Truth-sensitive implementation/provider changes must refresh applicable current-state docs and pass `Documentation Truth` on the exact PR head. The same verifier runs after merge.

Do not freeze “current main” or “current provider truth” in durable prose. Exact SHAs belong in historical evidence; current identity is resolved at use time.

## Scope

Appropriate:

- repository-grounded technical research;
- current provider/API verification;
- source-backed architecture comparisons;
- security/reliability research;
- metrics/observability patterns;
- implementation-ready research packets;
- contradiction checks between docs and runtime;
- truth-age/supersession analysis; and
- bounded MCP reads/writes when the exact action is exposed and separately authorized.

Not appropriate:

- exposing private data or sauce to external search;
- treating search summaries as production proof;
- broad autonomous rewrites;
- bypassing founder/review gates;
- converting another agent's recommendation into approval;
- claiming a repo fix works without repository/test/runtime evidence; or
- carrying yesterday's provider result forward as today's truth without revalidation.
