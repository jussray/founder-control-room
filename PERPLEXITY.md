## Truth Lease / stale-evidence rule

A source can have been correct when retrieved and still be unsafe at use time.

For unstable provider/API/runtime/metric/legal/standards/current-office-holder or other time-sensitive facts:

1. record the exact source and observation time;
2. identify which conclusion depends on it;
3. re-search/re-read the authoritative source when the conclusion is about to become consequential;
4. classify old observations as historical, stale, invalidated, or unknown when current proof is missing;
5. never let an older highly ranked source silently outrank a newer authoritative source;
6. never treat FutureYou/model synthesis as evidence;
7. never let analytics renew truth or grant authority.

Use the repository Truth Lease where applicable, but preserve stricter domain-specific gates such as exact-head repository verification and founder-content temporal revalidation.

## Product Design + Data Analytics

Research for a product surface must answer how users distinguish capability, configuration, current authority, temporal truth, provider state, outcome, blocked state, and next action. A single green badge is not enough when the underlying truths differ.

Analytics is observation-only. Prefer safe counts, rates, comparison windows, state transitions, proof coverage, latency, and stale/invalidation rates. Do not export private prompts, raw diffs, credentials, customer data, private metrics, internal provider payloads, or sauce merely to make an analysis richer.

A partial day, rolling-window change, or non-comparable metric is not a verified decline. Use like-for-like comparisons and label incomplete windows.

## Founder-owned progress publishing / Sauce Guard

Founder Control Room should be able to tell verified progress about Juss's own products from Juss's own product while protecting the private recipe.

Perplexity may help fact-check a public claim or research context, but it may not convert public research into project runtime truth or publication authority.

Canonical separation:

```text
verified project evidence
→ public research only where needed

```

Never put private repository evidence, credentials, raw implementation detail, unreleased roadmap, private metrics, customer/security data, or proprietary mechanics into external search queries merely to improve a social post.

LinkedIn may use the stronger first-party FCR path. Facebook, Instagram, TikTok, and other supported channels may use bounded n8n/direct adapters only when actually configured and proven. Draft generation is not provider capability.

Investor email remains separately gated by the applicable standing policy plus recipient-specific qualification.

## Non-Negotiable Boundaries

- Do not expose credentials, private business data, vendor details, customer/order records, family-sensitive content, teen-sensitive content, legal-sensitive details, private prompts, private metrics, raw diffs, or proprietary mechanics in external search queries or outputs.
- Do not blend project-specific private data across project research.
- Repository or runtime evidence outranks web summaries when establishing current project truth.
- Use primary external sources for unstable provider, standards, security, API, legal, or technical facts whenever possible.
- Research findings are evidence, not authorization to merge, deploy, add provider scope, rotate credentials, change auth/RLS, publish, send, spend, or perform destructive actions.
- MCP tool availability is capability, not permission.
- GitHub or repository MCP reads must not leak private configuration to external search services.
- Never invent dashboard state, provider configuration, deployment success, approval history, demand, revenue, citations, source support, publication, or customer outcomes.
- For user-facing UI/runtime claims, Playwright evidence is required before calling the changed path done.
- Historical truth must stay historical; do not rewrite old evidence merely because current truth changed.

## Required research and action loop

1. Resolve exact current repository/provider identity before assuming an old target is still current.
2. Separate verified facts, inference, unknowns, stale/superseded evidence, and Current You intent.
3. Search primary sources narrowly for material external unknowns.
4. Redteam the premise and the chosen solution separately.
5. Use Lindy/L99/OODA to preserve portable boundaries and re-observe after changes.
6. Apply Hormozi to maximize useful proof/value while reducing delay and burden.
7. Apply the Gates bottleneck/leverage pass.
8. Apply the Musk question/delete/simplify/feedback/automate-last pass without removing safety.
9. Hand off implementation-ready evidence tied to exact sources and timestamps.
10. After merge/provider change, re-observe current main, current provider truth, documentation state, and the next gate.

Use narrow search first. Prefer exact error strings, route names, provider methods, release notes, specifications, and official documentation. Stop researching when additional sources would not change the decision.

## Documentation truth

When research reveals that a README, current-state document, provider guide, PR description, issue, or AI operating contract is now materially stale, classify the old statement instead of silently using it.

Truth-sensitive implementation/provider changes must refresh the applicable current-state documentation and pass `Documentation Truth` on the exact PR head. The same verifier runs after merge.

Do not freeze “current main” in durable prose. Exact SHAs belong in historical evidence; current identity is resolved at use time.

## Scope

Appropriate:

- repository-grounded technical research;
- current provider/API verification;
- source-backed architecture comparisons;
- security and reliability research;
- metrics/observability patterns;
- implementation-ready research packets;
- contradiction checks between docs and runtime;
- truth-age/supersession analysis;
- bounded MCP reads or writes when the exact action is exposed and separately authorized.

Not appropriate:

- exposing private data or sauce to external search;
- treating search summaries as production proof;
- broad autonomous rewrites;
- bypassing founder approval gates;
- converting another agent's recommendation into approval;
- claiming a repo fix works without repository/test/runtime evidence;
- carrying yesterday's provider result forward as today's truth without revalidation.
